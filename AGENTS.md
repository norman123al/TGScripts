# PixInsight development and release guide

Use this guide for changes to TGScripts code, documentation, dependencies, and update packages. The CPD rules govern the whole product, including bundled helpers, external services, and downloaded data. Version 1.0.2 was published October 29, 2026 and lists December 12, 2026 as its effective date. Rule 10.2 gives existing CPDs 60 days from notification to comply. Check the live rules when preparing a release. [Certified PixInsight Developer Program Rules](https://pixinsight.com/security/cpd-rules/)

## Scripts and user data

- Implement script functionality on PixInsight through documented PJSR interfaces. Use documented interfaces to work with standard PixInsight components. Avoid product names or claims that imply PTeam endorsement or that present a tool as a replacement for a standard PixInsight component. See rules 5.8, 5.10, and 7.
- Keep runtime writes, caches, temporary files, and recovery data outside the PixInsight installation. Use the PJSR settings API for script preferences. For user-selected paths, reuse the shared `TGFileProtection` checks before writing, replacing, moving, or deleting. Preserve core-owned data and other developers’ files and settings. Never request elevated privileges or change security preferences. See rules 4.3–4.6 and 5.7.
- Ship executable code through the signed PixInsight distribution flow. Never fetch executable code for use outside the updater. Launch an external utility only for a purpose allowed by rule 5.3, with the user’s knowledge and with its use documented. Keep processing of PixInsight-managed images inside the platform. Use the documented PixInsight command-line and IPC interfaces for external control. Stellarium file import and export are permitted interoperability. See rules 5.1–5.10.
- Use secure network protocols and verify the integrity of downloaded data before use. For each connection, document the trigger, destination, and transmitted fields. Document external programs and file locations outside the installation, including temporary and recovery locations. Obtain explicit, informed consent for personal data collection or transmission, subject to the narrow licensing exception in rule 6.2. Telemetry requires explicit opt-in. Keep ads out of distributed interfaces and documentation. Never obtain unauthorized access, circumvent license protections, or include material from reverse engineering PixInsight. See rules 4.6 and 6.
- Record the source, version or retrieval date, license, and applicable redistribution terms for each bundled or downloaded third-party component or dataset. Include required notices in the shipped files. Include PCL acknowledgments where applicable. See rules 3.4 and 7.3.

## Update packages

1. Use standard PixInsight installation and update paths. Stage only files owned by TGScripts. Keep package entries in permitted deployment directories. TGScripts uses `src/scripts/TGScripts/` for scripts, libraries, and their signatures and `doc/scripts/<script-id>/` for compiled help. Review every `<remove>` path against files deployed by this repository. See rules 4.1–4.5 and PixInsight’s *Update Repository Reference*.
2. Keep each featured script’s `#feature-id` stable unless the change calls for a new identifier. After executable source or a bundled include changes, regenerate affected `.xsgn` files using PixInsight’s signing tools and keep each one beside its script. Protect the signing key and keep it out of source control, packages, logs, and review artifacts. Report suspected compromise to PTeam within 72 hours and keep CPD contact details current. See rule 3 and PixInsight’s *Code Signing System*.
3. Compile changed PiDoc help and verify its packaged paths and local references. Build `TGScripts_repository/TGScripts_repository.tar.gz` from the staged files. Compare its contents to the release sources, then record the archive’s SHA-1 and release date in `TGScripts_repository/updates.xri`. Sign the finalized manifest. Regenerate its signature after subsequent manifest changes. See rules 4.1–4.2 and PixInsight’s *Update Repository Reference*.
4. Use PixInsight to verify the packaged script signatures and the manifest signature. Test the changed script on the advertised minimum supported PixInsight version and build, and record the build used. For changes that touch network, filesystem, or external program behavior, exercise the affected path, including error handling. Record any unverified checks in the release PR.

PTeam can grant written exceptions for the specific rules listed in rule 5.6. Keep the authorization and its conditions with the release records. Respond to PTeam review requests within the timeframe described in rule 8.2.
